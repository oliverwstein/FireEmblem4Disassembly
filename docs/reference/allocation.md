# Memory, math and random numbers

The library under every system: three ways of laying out variable data in RAM (struct arrays, RAM areas, offset tables), block copies, calls through tables of pointers, multiplication and division, and the random number generator. The code is in [engine/core/lib/](../../engine/core/lib/), mostly bank `$82` (the RAM structures) and `$80`.

Per-routine details: [routines/core.md](routines/core.md) (generated by `tools/reference.py`).

## Struct arrays

A struct array is a 4-byte header (`structRAMStructHeader`) followed by fixed-size entries, numbered from 1:

| Byte | Field | |
|---|---|---|
| 0 | `CurrentStructCount` | entries in use |
| 1 | `MaxStructCount` | room |
| 2 | `StructSize` | bytes per entry |
| 3 | `Flags` | bits 0-1 a size class (0 for 1 byte, 1 for 2, 2 for 3, 3 for 4 and up); `$80` makes adding and removing do nothing, and nothing sets it |

`rlBuildRAMStructHeader` builds one (count `wR0`, size `wR1`, at `lR18`). For entries of 4 bytes or more it keeps one entry's room past the last as scratch, so `MaxStructCount` is one less than asked; `rlMoveRAMStructEntry` moves an entry through it.

Every routine takes the array in `lStructPointer2` and the entry in `lStructPointer1`. An entry of 1-3 bytes travels in `lStructPointer1` itself; a bigger one is copied from or to where `lStructPointer1` points. `wStructIndex` is the entry number.

| Routine | Does |
|---|---|
| `rlAppendNewStructEntry` | adds after the last; returns its number |
| `rlAddStructEntry` | adds at `wStructIndex`, shifting the later entries up (or at the end, if past it) |
| `rlInsertRAMStructEntryAt`, `...After` | finds the entry in `lStructPointer1` and adds `lPendingStructEntryPointer`'s at or after it |
| `rlRemoveRAMStructEntryByID`, `rlRemoveRAMStructEntry` | removes by number, or the entry equal to `lStructPointer1`, shifting the later ones down |
| `rlFindRAMStructEntry` | the number of the first entry equal to `lStructPointer1`, or 0 |
| `rlLoadRAMStructDataByIndex`, `rlSaveRAMStructDataByIndex` | read or write entry `wStructIndex` |
| `rlGetRAMStructEntryPointerByStructIndex` | a pointer to the entry, in `lStructPointer1` |
| `rlGetRAMStructCurrentStructCount`, `...MaxStructCount`, `rlSetRAMStructMaxStructCount` | the header |
| `rlMoveRAMStructEntry...` (5) | move an entry first, last, back, forward or to a number; nothing calls them |

Adding to a full array returns carry set; asking for an entry past the count returns carry set. `rsGetRAMStructOffset` multiplies the number by the size with shifts and adds (no hardware multiplier).

Struct arrays hold, among others, the battle's rounds (`aBattleRoundsData`, also built by the demo battles), the item records and inventories ([items.md](items.md)), the map menus' option lists ([map_menu.md](map_menu.md)), the chapter event data, the save code's lists and the generation change's (21 places build one).

## RAM areas

A RAM area is a block of RAM managed as a heap. It starts with a `structRAMAreaHeader` (8 bytes); entries follow up to `AreaEnd`, each a 6-byte `structRAMAreaEntryHeader` and its data:

| Entry field | Meaning |
|---|---|
| `Flags` | `$80` free; `$40` allocated in place; 0 allocated through a handle, movable |
| `Size` | the entry's size, its header included; the next entry starts that far on |
| `BaseTable` | the area (in place) or the handle (movable) |

The area's `Flags`: `$80` built without handles, `$40` compacted, `$20` an entry was allocated, `$10` one was freed.

**Building.** `rlBuildRAMAreaHeaderAndGuidingEntry` takes the size in A and the place in `lR18`, makes the area current (`lRAMAreaPointer`) and turns the rest of it into one free entry. With `wStructIndex` not 0 it sets `$80` and allocates no handles; with 0 it allocates a first block of `wRAMAreaHandlesPerBlock` handles inside the area. The areas the game builds:

| Area | Built by | `wStructIndex` |
|---|---|---|
| `aUnitRAMArea`, `aStaticUnitRAMArea`, `aDynamicUnitRAMArea`, `aHolyAndEnemyRAMArea`, `aInventoryRAMArea`, `aLoverRAMArea` | [generations.asm](../../engine/units/generations.asm) | 1 |
| `aMapMenuRAMArea` (`$0E57` bytes) | the map setup, `rsResumeMapAfterMenu` | 1 |
| `$7FB16C` (`$4E93` bytes) | the castle screen's setup | 1 |
| `$7F5709` (`$A8F6` bytes) | the world map's and the epilogue's setups | not set; whatever it holds |
| `$7FA500` | the unused screen (`$16`) | not set |

`rlLoadRAMAreaPointer`, `rlSaveRAMAreaPointer`, `rlBufferAndLoadNewRAMAreaPointer` and `rlLoadBufferedRAMAreaPointer` switch between areas through `lRAMAreaPointer` and its buffer.

**Allocating.** `rlAllocateRAMArea` takes a size in A and returns the data's address in `lR25`:

1. `rsFindFreeRAMAreaEntry` looks for the first free entry with room for the data and a header (`rsCheckIfEntryFitsInRAMArea`, first fit from the area's start).
2. The new entry is cut from the end of the free one. If fewer than 7 bytes of the free entry would be left, it takes the whole of it.
3. It is marked `$40` with the area in `BaseTable`.

The unit pools, the inventory, the map menus and the save code allocate this way (`rlAllocateRAMArea`: 18 calls). `rlCopyDataToRAMArea` copies data into an entry.

**Freeing.** `rlRemoveRAMAreaEntry` (the data's address in `lR25`) marks the entry free; `rsCombineAdjacentFreeRAMAreaEntries` then walks the whole area and merges every run of free entries into one.

**Running out.** When no free entry fits, `rsFindFreeRAMAreaEntry` compacts the area (`rlCompactRAMArea`: each movable entry after a free one slides down over it and its handle is updated) and looks again. If nothing fits then, it sets `CGADSUB` and `COLDATA` (a tint over the screen) and runs into a `BRK`: the game stops.

**Handles.** A handle block is a link to the next block, a count, and that many 4-byte handles: a long pointer to an entry's data and a status byte (`$80` free). `rlAllocateRAMAreaWithHandle` allocates a movable entry and returns a pointer to its handle; `rlCopyDataToRAMAreaHandle` writes through one; `rlFreeRAMAreaByHandleUnused` frees one. None of the three has a caller, and the areas that set `wStructIndex` have no handles. Every entry the game allocates is fixed, so compaction never has anything to move, and a full area always ends in the `BRK`.

## Offset tables

An offset table holds variable-size entries behind a list of word offsets: offset i is where entry i starts, counted from the table's start, and the last offset is where the free space starts. The first offset is therefore twice the number of entries plus 2, and an empty table is a single word of 2.

| Routine | Does |
|---|---|
| `rlAddOffsetTableEntry` | adds `wR0` bytes from `lR19` to the table at `lR18`, moving every entry along to make room for the new offset |
| `rlInsertOffsetTableEntry` | inserts at entry A |
| `rlUpdateOffsetTable` | replaces entry A with `wR0` bytes from `lR19`, moving the later entries by the change in size |
| `rlShiftOffsetTableEntry` | moves one entry by `wR0` bytes and fixes its offset |
| `rlCopyOffsetTableEntry`, `rlRemoveOffsetTableEntryUnused`, `rlCopyAllOffsetTableEntriesUnused`, `rlGetOffsetTableCountUnused` | nothing reaches them |

Only the factions use offset tables (`aFactionArea`, [factions.asm](../../engine/units/factions.asm): one add, three updates).

**The byte stack.** `rlInitByteStackAreaUnused`, `rlPushByteStackAreaUnused`, `rlPopByteStackAreaUnused` and their pointer routines keep a stack of bytes in a block whose address is at `$055F`. Nothing calls them.

## Block copies

`MVN` and `MVP` take their source and destination banks as operands, so a copy between arbitrary banks needs code written at run time. `rsInitBlockCopyRAMStubs` (at boot) copies two stubs to RAM; `rlBlockCopyMVNByRAM` and `rlBlockCopyMVPByRAM` write the banks of `lBlockCopyDestination` and `lBlockCopySource` into their stub, load `wBlockCopySize` - 1 and the two addresses, and call it. `MVN` copies upward, for a destination below the source; `MVP` downward. Only the offset tables use them (the struct arrays move entries a byte at a time).

`rlCallIndirectRoutineFromTable` calls entry A of a table of long pointers (the table's address at X), skipping a 0 entry; `rlJumpIndirectRoutine` jumps to `lR23` with the data bank set to its bank.

## Math

On the hardware multiplier and divider, with the scratch registers ([math.asm](../../engine/core/lib/math.asm)):

| Routine | Inputs | Outputs |
|---|---|---|
| `rlUnsignedMultiply16By16` | `wR10` × `wR11` | `wR12`-`wR13` (32 bits) |
| `rlUnsignedMultiply16By16High` | `wR34` × `wR35` | `wR36` (32 bits) |
| `rlUnsignedMultiply32By32` | `wR11` × `wR12` | `wR14` (64 bits) |
| `rlUnsignedDivide16By8` | `wR13` / `wR14` | `wR13` quotient, `wR10` remainder |
| `rlUnsignedDivide16By16` | `wR36` / `wR37` | `wR36` quotient, `wR34` remainder |
| `rlUnsignedDivide16By16R13` | `wR13` / `wR14` | `wR13`, `wR10` |
| `rlSignedDivide16By16R13` | the same, `wR13` signed | |
| `rlUnsignedDivide32By32` | `wR12`-`wR13` / `wR14`-`wR15` | `wR12`-`wR13`, `wR10`-`wR11` |
| `rlSplitNumberIntoDigits` | a number | its decimal digits (`aSplitNumberIntoDigitsTable`: 10, 100, 1000 ...) |

`rlSignedMultiply32By32Unused` and `rlSignedDivide32By32Unused` are reached by nothing.

## Random numbers

The generator ([random.asm](../../engine/core/lib/random.asm)) is a table of 55 numbers 0-99 (`aRNArray`) and a position (`wRNIndex`).

- **Seeding.** `rlInitRNArray` fills the table from a seed, `bFrameCounterByOnes & $3F`, by the subtractive method (each entry the difference of two others, mod 100, stepping by 21), then shuffles it three times. Its only caller is the opening logo's setup at boot, after RAM was cleared and before any VBlank has run, so the seed is always 0 and the table starts the same at every power-on and soft reset.
- **Rolling.** `rlGetRandomNumber` moves to the next entry and returns it minus 1 (0 becomes 99): a number 0-99. Every 55 calls it reshuffles the table in place (`rsShuffleRNTable`: each entry minus the one 31 further on, mod 100) and checks the code checksums.
- **Saved.** `rsSaveGeneralSaveData` writes the 55 numbers and the position into the save (7 bits each), and `rsLoadGeneralSaveData` restores them. Loading a save gives the same sequence of rolls each time.
- **Chances.** `rlRollForChance` ([effects.asm](../../engine/battle/effects.asm)) rolls and compares with a percentage: success when the roll is below it. `rlGetRandomNumber100` returns a number from 0 to A - 1 (the roll × A / 100). `rlConvertChanceToFullByte` turns a percentage 0-100 into 0-256 (`aChanceToByteLookupTable`).

**The checksum hook.** After each reshuffle `rlGetRandomNumber` calls `rlCheckCodeChecksums` ([frame.md](frame.md)). If it returns carry set, `rsRigRNArrayByPlaytime` takes the play time (`rlGetGameTimeHoursMinutes`), computes hours × 16 + minutes / 4 - 80, held to 0-100, and sets every table entry below that to 0, which rolls as 99. A modified ROM's luck worsens the longer the game has run: nothing changes in the first five hours, and from 11 hours 16 minutes on every roll is 99, so only a chance of 100 succeeds. The checksums match in the released ROM.

## Open questions

- **The `$80` struct flag** would make an array read-only; nothing sets it.
- **The epilogue's and world map's area** take `wStructIndex` as whatever it was. If it was 0 they get a handle block that nothing uses; either way nothing allocates with handles.
