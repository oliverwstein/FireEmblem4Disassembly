# Getting graphics in

Graphics reach VRAM in three stages: compressed data in ROM is unpacked into RAM by the decompressor, usually through a queue the main loop works through; the DMA queue carries it to VRAM in VBlank ([frame.md](frame.md)); and colors live in a palette buffer that fades change a step at a time. This page covers the decompressor and its queue, the brightness fades and the procs that run them, palette fading, the shared palette data, and the tilemap and layer helpers. The code is in `engine/core/graphics/`.

Per-routine details: [routines/core.md](routines/core.md) (generated by `tools/reference.py`).

## The decompressor

`rlDecompressor` (`$80/AA02`) unpacks one stream from `DecompressionVariables.lSource` to `lDest`. A stream is a series of methods, each starting with a byte ([tools/decompress.py](../../tools/decompress.py) has the full format):

| First byte | Method |
|---|---|
| `$00`-`$3F` | literal: (b & `$3F`) + 1 bytes follow |
| `$40`-`$4F` | nybble fill: bytes made from the nybbles that follow and a fixed nybble |
| `$50`-`$5F` | each following byte written twice |
| `$60`-`$7F` | a fixed byte before (or after) each of the following bytes |
| `$80`-`$DF` | copy from earlier output (1- and 2-byte forms) |
| `$E0`-`$F7` | runs of one byte (long and short forms) |
| `$F8`-`$FD` | copy from earlier in the compressed stream itself |
| `$FE`, `$FF` | the end |

A stream in the lower half of a bank continues at `$0000` of the next bank when it reaches `$8000`; one in the upper half continues at `$8000` of the next. Other entry points: `rlDecompressSingle` (source `lR45`, destination `lR47`), and `rlDecompressLinear`, which reads the sound data across banks. `tools/decompress.py` reproduces it byte for byte. The 1,647 streams in `gfx/` take 2.19 MB of the ROM and unpack to 8.4 MB.

**The build.** Each stream is kept as an editable file (an indexed `.4bpp.png`/`.2bpp.png`, or a `.bin`) beside the original stream, `NAME.*.comp`. `tools/gfx.py lz` reuses the original bytes when they still decompress to the file and compresses with `tools/compress.py` otherwise; `tools/stream_layout.py` places each region's streams in order (its `.streams` list, with a start and end address), crossing bank halves as the decompressor does, and fails if they overflow the end. See [docs/AUTHORING_GRAPHICS_PLAN.md](../AUTHORING_GRAPHICS_PLAN.md).

**The queue.** Decompression is slow, so most of it is queued and done in the main loop, outside VBlank:

1. `rlAppendDecompList` adds an entry (`structDecompressionEntry`: source `lR18`, destination `lR19`, both long) at `wDecompressionArrayPosition` and writes a 0 source after it. With the screen blanked it runs the queue at once.
2. `rlDecompressByList`, from the main loop routine (`rsRunFrameTasks`, `rsMapMainLoop`), runs every entry until a 0 source and empties the queue.

The queue (`aDecompressionArray`) is `$20` bytes, room for five entries. The fifth's end marker (three 16-bit stores at `+6`, `+7`, `+8`) spills two bytes past the array onto `bFrameCounterByOnes` (`$0469`) and `bFrameCounterByThrees` (`$046A`); nothing checks for a sixth, which would be written over the frame counters and the random number table. `rlDecompressByList` hangs in an endless loop if it reads past `$20` bytes.

A screen that needs the data in VRAM unpacks it into a RAM buffer and then DMAs the buffer. Openers work with the screen blanked, where both run at once. During play the DMA must wait: `rlDecompressByList` clears `bDecompressionArrayFlag` only after the last entry, and a stream can take several frames of main loop time, so code polls the flag before queuing the copy: the battle scene's loader (`bBattleSceneDecompState`: 1 unpack then copy, 2 copy, 3 unpack), `rlMapBattleWaitDecompression` (sets proc bit `$0001`), the map magic, the event unit movers, `combatants.asm`. There are 61 calls to `rlAppendDecompList` (one in `procDecompressToBufferUnused`), 32 calls to `rlDecompressSingle`, and 55 direct calls to `rlDecompressor` (the title, logo, world map, its markers and highlights, the minimap, game over, records, the opening demo).

`procDecompressToBufferUnused` ("De") would queue a stream into `aDecompressionBuffer` and end when the queue is empty; nothing creates it.

## Brightness fades

The screen's brightness is the low nibble of `bBufferINIDISP`, written to `INIDISP` every VBlank ([frame.md](frame.md)).

**By a timer.** `rlFadeInByTimer` and `rlFadeOutByTimer` ([fade.asm](../../engine/core/graphics/fade.asm)) take a number of frames per step in A and are called once a frame. On the first call (`wScreenFadingFlag` negative) they start the timer; every A frames they move the brightness one step; when it reaches 15 (in) or 0 (out) they return carry set and set the flag negative again. A fade-out ends with forced blank on. A full fade takes 15 × A frames.

**The fade procs** ([procs.md](procs.md)) call those every frame and end themselves when they are done:

| Proc | Name | Speed |
|---|---|---|
| `procFadeIn`, `procFadeOut` | `FI`, `FO` | one step a frame |
| `procFadeInByScreenFadingTimer`, `procFadeOutByScreenFadingTimer` | `FI`, `FO` | `wScreenFadingProcInput` frames a step |
| `procMainLoopChangeFade` | `Bt` | starts `procFadeOut`, then installs the opener in `wInput0` ([game_states.md](game_states.md)) |
| `procMainLoopChangeFadeByTimer` | `Bt` | the same with `procFadeOutByScreenFadingTimer` |

`procFadeIn` is created in eight files (screen setups, the dialogue procs, the save screen; `map_cursor.asm` only checks whether one is running); nothing but `procMainLoopChangeFade` creates `procFadeOut`. The event engine has fade procs of its own (`procEventFadeInByTimer`, `procEventFadeOutByTimer`, [events.md](events.md)). All the fades share one timer, so two at once would interfere. `rlClearAllFadeProcs` frees every fade-in and fade-out proc, the events' included, and sets the flag back.

## Palette fading

The palette fades change colors in `aBGPaletteBuffer` (offsets `>= $0100` reach `aOAMPaletteBuffer` right after it) toward a target, one step per call ([palette_fade.asm](../../engine/core/graphics/palette_fade.asm)). They share `aPaletteFading`: `wMaxSteps`, the steps in a whole fade; `wCurrentStep`; `wDesiredColor`. A caller sets `wMaxSteps`, then calls the fade once a frame with carry clear (or set, to stop halfway at `wMaxSteps / 2` steps without changing the interpolator's `wMaxSteps` — used to dim backgrounds partway for map magic) until it returns carry set. Each takes its arguments inline after the call and returns past them:

| Routine | Inline arguments | Fades toward |
|---|---|---|
| `rlFadePaletteToColors` | source (in bank `$7E`), color count, palette offset | the colors at the source |
| `rlFadePaletteToBlack` | a pointer to a list of (offset, count) pairs ended by `$FFFF` | `wDesiredColor` (black when it is 0) |
| `rlFadeBGPaletteColorRanges` | a pointer to a list of (offset, count, color) ended by `$FFFF` | each range toward its color (`rlDarkenBGPaletteRange`) |
| `rlSavePaletteBufferColorsToRAM` | destination (long), count, palette offset | copies colors out of the buffer, to fade back to them later |

`rlFadeFromToColorByStep` makes one color: each of the three 5-bit channels goes from the current value toward the target by `rsInterpolateColorChannel`. Step 0 returns the current value and step N + 1 the target; step k returns current + (target - current) / (N - k + 1), in 8.8 fixed point on the hardware divider, truncated. The fades pass the buffer's current color, so each step covers an equal share of what is left: linear, landing on the target at step N. Users: the map battle's magic, the conversation scenes, the first generation's ending, the save menu, the title and the world map.

`rlFadeOutCOLDATAByTimer` and `rlFadeInCOLDATAByTimer` fade the fixed color (`COLDATA`, used by color math) by the same timer; nothing calls them.

## Tilemaps and layers

- `rlFillBG2Page0TilemapBuffer`, `rlFillBG2Page1TilemapBuffer`, `rlFillBG3Page0TilemapBuffer` fill a page of `aBG2TilemapBuffer` or `aBG3TilemapBuffer` with the tile word in A (the map, the logo, dialogue, the save menu).
- `rlSetLayerPositionsAndSizes` sets the VRAM addresses of the four layers' tiles (`wR1`-`wR4`), the sprites' tiles (`wR5`) and the four tilemaps (`wR6`-`wR9`), all as VRAM word addresses, into both the `BG12NBA`, `BG34NBA`, `OBSEL` and `BG1SC`-`BG4SC` hardware registers and their buffers. It does nothing unless `bBufferINIDISP` has forced blank set. Twenty-four files call it, every screen opener among them.

## Open questions

- **Appending during a run.** `rlDecompressByList` resets `wDecompressionArrayPosition` to 0 before it starts. An `rlAppendDecompList` from VBlank while the main loop is still unpacking would write at entry 0 and put an end marker at entry 1, cutting off the entries not yet run. Code that waits for the flag before queuing avoids it; whether any path appends mid-run is not checked.
- **The queue's size.** Whether any screen queues five decompressions at once (where the fifth's end marker spills two bytes onto the frame counters) is not checked.
