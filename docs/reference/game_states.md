# Game states and screens

A screen (the castle, the map, the status screen, a battle) is three things installed together: a main loop routine, a VBlank routine, and one or two entries of the game state table that run every frame inside VBlank. This page covers the game state table and its dispatcher, the pattern every screen follows (an opener, a setup, an upkeep and a step), how one screen hands over to the next, and the table of per-frame engines that run after the game states. The frame around them is [frame.md](frame.md).

Per-routine details: [routines/core.md](routines/core.md) (generated by `tools/reference.py`).

## The game state table

`aGameStateRoutines` (`$80/9B01`) is 56 long pointers. Every frame the VBlank routine calls `rlRunGameStateRoutines`, which runs the entry numbered `wGameStateRoutine1` and then the one numbered `wGameStateRoutine2`, each with the data bank set to the routine's bank (`rsDispatchGameStateRoutine`). Entry 0, `rlGameStateNone`, does nothing, so either variable can be idle.

The dispatcher has one more rule: an entry whose bank byte is `$7D` is not called; its low word is written to `wGameStateRoutine1`. No entry in the table has that bank.

Most screens own three consecutive entries:

| Entry | Kind | Selected by | Runs |
|---|---|---|---|
| 3k + 1 | upkeep (`rl<Screen>Upkeep`) | the opener, in `wGameStateRoutine2` | every frame while the screen is up: sprites, scroll arrows, sometimes input |
| 3k + 2 | setup (`rl<Screen>Setup`) | the opener, in `wGameStateRoutine1` | once: turns on sprites, picks a first step, starts a fade-in; ends with `inc wGameStateRoutine1` |
| 3k + 3 | step (`rl<Screen>Step`) | the setup's increment | every frame after that: calls the routine for `wGameStateStep` from the screen's own step table |

The battle scene and the title screen have no upkeep; their openers leave `wGameStateRoutine2` at 0. The setups end with `inc wGameStateRoutine1` (18 places).

**`wGameStateStep`** is the screen's own state. Openers clear it; the step routine dispatches on it and the step routines change it. The status screen has 11 steps (`aStatusScreenSteps`), the chapter map 13 (`aMapStepRoutines`). Other systems read the game state to know what is going on: the AI runs only while `wGameStateRoutine1` is `GAMESTATE_MAP_STEP`, and `rlProcEventWaitBattleSceneEndCycle` waits while it is `$18`-`$1B` (the battle scene, and by the range the title screen).

## Openers and changing screens

An **opener** is a main loop routine (`rsOpenStatusScreen`, `rsOpenCastleScreen`, `rsOpenBattleScene`, `rsReturnToMapMainLoop` ...). It runs once, in the main loop, so the VBlank routine is not in the middle of the old screen while it works. `rsOpenStatusScreen` is typical:

1. blank the screen, install the screen's VBlank routine and wait for VBlank, then turn VBlank off;
2. reset the registers (`rlHardwareResetScreenPosMathHDMA`, `rlHardwareResetScreenRegisters`) and set the layers' VRAM addresses (`rlSetLayerPositionsAndSizes`);
3. reset the engines it will not share: the window procs, the active sprites, the IRQ and HDMA engines;
4. load the screen's graphics and variables;
5. set `wGameStateRoutine1` to the setup, `wGameStateRoutine2` to the upkeep and `wGameStateStep` to 0;
6. install the screen's main loop routine (here `rsRunFrameTasks`) and turn VBlank back on.

The old screen installs the opener in one of three ways:

- `procMainLoopChangeFade` (41 places) or `procMainLoopChangeFadeByTimer` (9), with the opener in `aProcSystem.wInput0`. Its init starts a fade-out proc unless the screen is already blank or dark; its on-cycle waits until it is, then installs the opener with `rlSetMainLoopPointer`, turns off the H and V timer IRQs and ends.
- `rlSetMainLoopPointer` directly (3 places). With bit `$0010` of `wEventEngineFlags` set it would save the routine in `wR26` instead; nothing sets that bit.
- A store to `wMainLoopPointer` (44 places), usually from another opener installing its screen's main loop.

`rsReturnToMapMainLoop` (22 places name it) is the way back to the chapter map from every other screen. It blanks the screen, turns VBlank off, resets the map's graphics and engines (`rsResetMapGraphicsAndSystems`), sets up the map display for `wMainGameMode`, loads the window and font graphics, the window registers and the row-upload IRQ, installs `rsMapMainLoop` and `rsMapVBlank`, and selects `GAMESTATE_MAP_STEP` with the step from `wSavedMapStep`. Then `rsResumeMapAfterMenu` rebuilds the map menus' RAM area, sets the step to 11 (the map step for a return), handles a defeated unit and resumes the phase music, and the screen is unblanked. `rsStartChapterMap` does the same for a new or resumed chapter, but selects `GAMESTATE_MAP_SETUP` and starts the chapter's events.

## The per-frame engines

After the game state routines, the VBlank routine calls `rlRunVBlankHooks`, which runs every routine in `aTaskTable`: 16 slots of 3-byte long pointers, from slot 15 down to slot 0.

`rlRegisterVBlankHook` takes a long pointer in `lR44` to an engine's action table, three words in one bank:

| Word | Used for |
|---|---|
| +0 | the init routine: run at once |
| +2 | the per-frame routine: stored in the highest free slot of `aTaskTable` |
| +4 | read only by `rlFindAndJumpTaskTableUnused`, which nothing calls |

It returns carry set when all 16 slots are taken. Since slots fill from 15 down and run from 15 down, the engines run in the order they were registered. `rlInitEngineAndStartLogo` clears the table (`rlResetVBlankHookTable`) and registers five, the only calls in the game:

| Order | Table | Init (+0) | Per frame (+2) | +4 | Page |
|---|---|---|---|---|---|
| 1 | `aProcEngineMainProcActionTable` (`$82/8000`) | `rlProcEngineResetProcEngine` | `rlProcEngineMainProcLoop` | `rlProcEngineStub` | [procs.md](procs.md) |
| 2 | `aActiveSpriteEngineMainActionTable` (`$81/8000`) | `rlActiveSpriteEngineReset` | `rlActiveSpriteEngineMainLoop` | `rlActiveSpriteEngineStub` | [sprites.md](sprites.md) |
| 3 | `aHDMAEngineMainActionTable` (`$82/C000`) | `rlResetHDMAEngine` | `rlHDMAEngineMainLoop` | `rlHDMAEngineStub` | [scanlines.md](scanlines.md) |
| 4 | `aIRQEngineMainActionTable` (`$82/E000`) | `rlResetIRQEngine` | `rlIRQEngineStub` (does nothing; the engine runs from the IRQ) | `rlIRQEngineRestoreDefaultIRQ` | [scanlines.md](scanlines.md) |
| 5 | `aEventEngineMainActionTable` | resets the dialogue engine, the active sprites, the event procs and the event state | `rlEventEngineMainLoop` | `rlEventEngineStub` | [events.md](events.md) |

Screens reset an engine by calling its init routine directly (`rlResetHDMAEngine`, `rlActiveSpriteEngineReset` ...); the table is only read at registration. So the procs step first each frame, and any active sprite, HDMA entry or event command they create is stepped later in the same frame.

## The main loop routine

`rsRunFrameTasks` ([boot.asm](../../engine/core/frame/boot.asm)) is the main loop routine of most screens:

1. `rlButtonCombinationResetCheck`: the soft reset ([frame.md](frame.md));
2. `rlDecompressByList`: the queued decompressions ([graphics.md](graphics.md));
3. `rlRunDeferredSoundUpload`: sound data waiting to go to the APU.

The chapter map's `rsMapMainLoop` runs the same, with the AI (`rlRunAIEngineCycle`, [ai.md](ai.md)) after the decompressions and `rlPlanQueuedMapSpriteMovement` last.

## Depends on

- [frame.md](frame.md): the VBlank routine calls `rlRunGameStateRoutines` and `rlRunVBlankHooks`.
- Each screen's own code for its openers, setups, upkeeps and steps.

## Open questions

- **The `$7D` redirect.** `rsDispatchGameStateRoutine` treats bank `$7D` as "set `wGameStateRoutine1`", but no entry uses it.
- **`wR26` from `rlSetMainLoopPointer`.** Only `rlEventEngineBeginScript` touches `wR26` (it clears it), and nothing sets the event flag that would store a routine there. Both look like an event-controlled screen change that was never used.
