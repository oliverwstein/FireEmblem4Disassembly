# Sound

The SNES's sound is a separate computer: the APU, an SPC700 CPU with 64 KB of its own RAM and a DSP that mixes eight voices of BRR-compressed samples. The main CPU reaches it only through four one-byte ports (`$2140`-`$2143`, `APUIO0`-`3`), each a pair of latches: a byte written on one side is read on the other. This page covers the 65816 side: uploading the driver and the sound data, the per-frame exchange of commands and status on the ports, the sound scripts that songs are, choosing the music, and the sound data in ROM. The SPC700 driver itself is not disassembled; what it does with a command is known only from how the game uses it.

Code: [engine/sound/driver.asm](../../engine/sound/driver.asm) (bank `$80`) and [engine/sound/music.asm](../../engine/sound/music.asm) (bank `$81`); data: [audio/](../../audio/) from `aSoundHeader` (`$F7/7C00`) to the end of the ROM.

Per-routine details: [routines/sound.md](routines/sound.md) (generated by `tools/reference.py`).

## The ports

Every VBlank routine calls `rlSendSoundQueuesToAPU` (the lag-frame path too, [frame.md](frame.md)):

| Port | Direction | Use |
|---|---|---|
| 0 | to the APU | `wSoundEffectCurrent`: a sound effect or a command. When the APU echoes it back on port 0 it has taken it, and the next value comes off `aSoundEffectQueue` |
| 2 | to the APU | `wSoundEffect2Current`, from `aSoundEffect2Queue`, the same way |
| 1 | from the APU | kept in `bAPUPort1`; compared with the first byte of the last decompressed chunk (script command 17) |
| 3 | from the APU | kept in `bAPUStatus` |

Each port carries at most one new value a frame. A queue holds four words; a fifth overwrites the last. Each port is read twice until two reads agree, since the APU may be writing it.

**Adding to the queues.**

| Routine | Queue | Skipped when |
|---|---|---|
| `rlPlaySoundEffect` (297 calls) | port 0 | an upload is running (`bAPUUploading`) or `bSoundFlags` bit 0 |
| `rlSendSoundCommand` | port 0 | never |
| `rlQueueSoundCommand` | port 0 | values `$C8`-`$DF` while `bSoundFlags` bit 4 (sound off); `$CB`-`$CD` are also kept in `bSoundResendCommand` |
| `rlPlaySoundEffect2` (46 calls) | port 2 | an upload is running or `bSoundFlags` bit 2 |
| `rlPlaySoundEffect2Checked` | port 2 | as above, but during an upload `$10` and `$20` are still queued, once |

Menus use effects `$06` (cursor), `$08` (confirm), `$21` (cancel). Port-2 effects are mostly the battle animations'.

**Commands** (values sent on port 0 from `$C0` up). Their meaning is the driver's; the uses show:

| Value | Used for |
|---|---|
| `$C0` | stop the song (debug sound test, X) |
| `$C8`-`$CD` | start the song just uploaded (script command 17: `$C8` 78 times, `$CB` 34, `$C9` 8, `$CC` 2, `$CA` 1); dropped while the sound is off; `$CB`-`$CD` are resent when it comes back on |
| `$E0` | fade the music out (13 places: before a battle, a level-up, game over, the phase change) |
| `$E1` | the fade before the victory theme (`rlCheckVictoryTheme`) |
| `$F7` | lower the music: a map battle (`rlMapBattleLowerMusic`, which sets `wMapBattleMusicLowered`), the gold pop-up, the castle courtyard (5 places) |
| `$E8` | raise it again: the end of a map battle, closing the gold pop-up, and in the castle (screen and courtyard), the status screen, the unit and item windows and the revive screen (8 places) |
| `$F2`, `$F3` | mono, stereo (`rlSoundOnFlag40Set`/`Cleared`) |
| `$F8` | sent when the sound is turned off while a song plays (`rlSoundOnFlag10Set`) |
| `$xxF1` | script command 17's alternative to `$CB`-`$CD` when the APU already holds the chunk (below) |

**`bAPUStatus` bits** as the code reads them: bit 1 a song is playing (`rlResumePhaseMusic`, `rlSoundOnFlag10Set`); bits 4-5 a fade is under way (the battle transition and `procFadeOutAndChangeSong` wait for them to clear); bit 7 mono is on.

**The sound option** (`rlApplySoundOption`): stereo clears bits 4 and 6 of `bSoundFlags`, mono sets 6, off sets 4. `rlUpdateSound` notices the change and sends `$F2`/`$F3` or `$F8`, and on turning the sound back on queues `bSoundResendCommand` again. Off keeps the sound effects.

## Uploading

**The driver.** `rlInitSound` (at boot, and by the anti-tamper screens) clears `$04B6`-`$0515`, sends the driver with `rlUploadToAPU`, then the upload list `aSoundStartUpload`. `rlUploadToAPU` speaks the APU's boot ROM (IPL) protocol: blocks of size, SPC address and bytes, one byte per handshake on ports 1 and 0, ended by a size of 0 and the address to run. The driver is five blocks: `$0200` (175 bytes), `$0660` (5,448), `$1BC0` (1,945), `$C502` (4), `$FF80` (32); it starts at `$0200`. Its ID text is `"ELM SND1960327W"`.

**Upload lists.** After that, data goes through the driver's own loader. `rlRunSoundUploadList` (list in `lR39`) writes the upload mode (`bAPUUploading`: `$FD`, `$FC`, `$FB` or `$FA`) to port 0, then for each chunk the list names sends its SPC address and its bytes two at a time (ports 2-3, with a counter on port 0), and ends with a size of 0. With `bSoundUploadNoVBlank` set it turns VBlank off for the duration. A list is words up to `$0000`:

| Word | Means |
|---|---|
| `$0064`-`$07FF` | upload that chunk |
| `$0001`-`$0063` | an indirect upload: `rsGetIndirectSoundUpload` returns the next chunk of list n each call |
| `$Cxxx` + word | the SPC address for the chunks that follow |
| `$Axxx` | read the battle's terrain into `aSoundTerrain` (`rsSoundUploadCommandReadTerrain`) |
| `$Bxxx` | forget what the decompression buffers hold, then as `$Fxxx` |
| `$Fxxx` | forget `aSoundIndirectLast` |
| `$9xxx` | clear `bSoundResendCommand` |
| `$Dxxx` | none: the chunk in the low bits |
| `$1xxx`-`$8xxx`, `$Exxx` | a relative jump; no list uses it |

**Chunks.** The chunk table (`aSoundChunks`, 773 entries from ID `$64`) gives each chunk its address, size, SPC address (0 = right after the previous chunk) and flags. Flag bit 0: compressed; it is unpacked with `rlDecompressLinear` into `$7E5358` (bit 1: `$7E6358`) first, unless that buffer already holds it (`wSoundBuffer1Chunk`, `wSoundBuffer2Chunk`). The 112 compressed chunks are the song sequences.

**Indirect uploads.** IDs 5-`$63` index `aSoundUploadLists` (68 lists). Asked for at the start of its list, an ID equal to the last one (`aSoundIndirectLast`, one slot for IDs below `$3C` and one from `$3C` up) uploads nothing: a song's instrument set that is already in SPC RAM is not sent again. IDs 1-4 depend on the battle. They read a byte at `$7E4EA9` plus `aSoundBattleStructOffsets`, which lands on fields of the action structs: 1 the defender's `WeaponID` (`aActionStructUnit2` + `$28`), 2 the attacker's `WeaponID`, 3 the defender's `ClassID`, 4 the attacker's `ClassID`. That byte indexes `aSoundHeader.BattleUploads` (weapons at offset 0 or `$A0`, classes at `$140`) for an upload list; for the classes the list is taken from `aSoundTerrainUploads` by the unit's terrain group (`aSoundTerrainGroups`; in chapter 4 every terrain but two counts as group `$10`).

## Sound scripts

A song is a **sound script** (`aSoundScripts`, 160 numbers): words up to `$0000`; bits 15-10 a command (0 none) whose argument is the next word, bits 9-0 frames to wait after it. Writing a script number to `wMusicID` starts it; bit 15 of `wMusicID` means upload with VBlank off.

`rlUpdateSound`, at the end of every VBlank routine, steps two channels: 0 runs `wMusicID`, 1 runs `wSoundScript1ID`, which nothing sets. `rsStepSoundScript` restarts a channel when its ID differs from `aSoundScriptRunning`, otherwise counts its wait down and runs commands to the next wait. At `$0000` the channel's ID goes into `aSoundScriptPrevious` and `wMusicID` returns to 0. So `wMusicID` is a request, cleared once its script has run; the song keeps playing on the APU, and `aSoundScriptPrevious` says which it was. `rlStepMusicScript` steps channel 0 at once and runs a deferred upload, for code that sets `wMusicID` and wants it started this frame.

| Command | Does | In the scripts |
|---|---|---|
| 1, 2 | `rlPlaySoundEffect` | |
| 3, 4 | `rlPlaySoundEffect2` | 9 |
| 5 | `rlSendSoundCommand` | 1 |
| 6 | `rlQueueSoundCommand`; bits 8-11 of the script ID (1-8) replace those of the argument | 1 |
| 7-10 | run an upload list now, mode `$FD`-`$FA`; while another upload runs, retry next frame | 0 |
| 11-14 | leave an upload list in `wSoundDeferredUpload` for the main loop, mode `$FD`-`$FA` | 141 (11), 2 (13) |
| 15 | wait until a bit of the argument is set in `bAPUStatus` | 0 |
| 16 | wait until the deferred upload has gone | 0 |
| 17 | once no upload is waiting, queue a command; for `$CB`-`$CD`, if the APU reports on port 1 the first byte of the chunk just decompressed, send `$xxF1` with that byte instead | 124 |
| 18 | queue `$C2`, or `$80C3`/`$80C4` for terrains 1, 4 and `$17`, by a battle unit's terrain | 12 |

The usual song script is two commands: a deferred upload of its data, then command 17 with `$C8` or `$CB`, which waits until the upload is done. **Deferred uploads** run from the main loop (`rlRunDeferredSoundUpload`, in `rsRunFrameTasks` and `rsMapMainLoop`), so a long upload is interrupted by VBlank instead of holding it; while it runs, `bAPUUploading` holds the port queues back.

[SONGS.md](../../audio/SONGS.md) lists every script with where it is asked for: code, events (`PLAY_SONG`), dialogue (`DIALOGUE_PLAY_SONG`) and the debug sound test.

## Choosing the music

([music.asm](../../engine/sound/music.asm); the phases are [map.md](map.md).)

- `rlStartPhaseMusic` sets `wPhaseSongID` for the active army and plays it. The player's phase: the chapter's song (`aPlayerPhaseChapterSongIDs`), or the victory theme (`$20`) when no enemy is left (`rlGetVictoryThemeIfAllEnemiesDead`). Another army: by its relation to the player, `SONG_ALLIED_PHASE` or `SONG_NEUTRAL_PHASE`, or for an enemy its name's song (`aNonPlayerFactionPhaseSongIDs`, 53 names). The chapter's first phase: `aChapterFirstPhaseSongIDs`.
- `rlResumePhaseMusic` plays `wPhaseSongID` again after an event or another screen, unless a song is playing and it is that one.
- `rlCheckVictoryTheme`: when the last enemy falls, the victory theme becomes the phase song and, outside events, `procFadeOutAndChangeSong` sends `$E1`, waits until `wMusicID` is 0 and status bits 4-5 are clear, starts the new song unless it is already the last one, and ends when its script has run.
- The battle songs: `rlGetBattleSong`, `rsSetStaffBattleSong` (`SONG_BATTLE_*`, [Sound.h](../../include/Sound.h)).

**Map sprite panning.** `rlUpdateMapSpriteSoundPanning` sends port-2 values for a moving map sprite's sound (`aSoundChannelFadeState`, two channels): a level from the sprite's state, with bit 7 and flags, one channel a frame by `bSoundUpdateSlot` (0, 3, 6).

## The data

`aSoundHeader` points at everything: the driver, the scripts, the upload lists, the chunk table, the start upload, the driver ID, the battle and terrain upload tables. Pointers are 16-bit with a bank relative to the header's; the data is read linearly across banks. In all, `$F7/7C00`-`$FF/FFFF`, 558,080 bytes. `tools/sound_kinds.py` sorts the 723 distinct chunks by replaying every upload into an image of SPC RAM:

| Kind | Count | SPC RAM | Files |
|---|---|---|---|
| sample | 158 | anywhere | `audio/samples/ID.brr` (9-byte BRR blocks), 736 KB |
| sequence | 112 | `$C500` (a few at `$B500`, `$BC00`, `$D400`) | `audio/sequences/ID.bin`, compressed in ROM |
| directory | 210 | `$FD00`-`$FDFF`, the DSP's sample directory (`DIR` = `$FD`) | `audio/directories/ID.bin` |
| instruments | 122 | `$FE00`-`$FEFF`, 6 bytes each | `audio/instruments/ID.bin` |
| other | 118 | small blocks at `$FF50`-`$FFF8`, three at `$2380` | `audio/chunks/ID.bin` |

A sequence is a list of patterns, each eight track pointers, one per voice. The build recompresses an edited sequence ([graphics.md](graphics.md) has the format). Directory entries are fixed SPC addresses, so a sample whose length changes moves the samples after it and their entries must change to match ([audio/README.md](../../audio/README.md)).

## Limits

| Limit | Where |
|---|---|
| One value a frame per port | `rlSendSoundQueuesToAPU` |
| Four queued values per port; a fifth overwrites the fourth | `rlPlaySoundEffect`, `rlPlaySoundEffect2` |
| One deferred upload at a time | `wSoundDeferredUpload`; commands 11-14 wait |
| No effects during an upload (except port-2 `$10`/`$20`) | `bAPUUploading` |
| SPC RAM layout fixed by the driver | `DIR` `$FD00`, instruments `$FE00`, sequences `$C500` |

## Open questions

- **The driver.** Not disassembled (`audio/driver/*.bin`). The meanings of the commands, of the four upload modes `$FA`-`$FD`, of port 1 and of the status bits come from their uses only.
- **The `other` chunks** at `$FF50`-`$FFF8` and `$2380`, and the three no replay reaches (`$339`, `$341`, `$342`).
- **`$xxF1`.** Script command 17 sends it in place of `$CB`-`$CD` when port 1 matches the chunk's first byte; perhaps "the sequence is already loaded, play it".
- **Channel 1** of the script engine is never started.
